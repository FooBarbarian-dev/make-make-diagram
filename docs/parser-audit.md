# pipeview parser conformance audit

Audit of `pipeview/parsers/make_parser.py` and `pipeview/parsers/gitlab_parser.py`
against real-tool semantics, motivated by two field reports: `export VAR ?= value`
lines flagged "Unparseable" on an ordinary Makefile, and a single `!reference` tag
destroying the parse of an entire `.gitlab-ci.yml` (error attributed to line 1).

**Method.** Every construct below was probed with a minimal throwaway input against
the parsers as of commit `4e9e2b5` — behavior *observed*, never inferred from
reading parser code. GNU Make rows were additionally cross-checked against
`make -pqn`'s database (targets, prerequisites, variable values and origin
comments) as ground truth. Probe environment: **GNU Make 4.3**, **PyYAML 6.0.1**,
Python 3.11. Make-4.4+ constructs (`:::=`) could not be ground-truthed locally and
cite the GNU Make manual instead. GitLab rows cite the GitLab CI/CD YAML reference
by section name (no network access during the audit).

**Verdicts.**
- `correct` — parser models the construct the way the real tool does.
- `wrong` — parser produces incorrect model data, silently (the worst class).
- `missing` — construct dropped with no diagnostic.
- `degrades-honestly` — not modeled, but an accurate named diagnostic says exactly
  what was skipped.

A generic "Unparseable line" warning on input real make accepts is classified
`wrong`, never `degrades-honestly`: it blames the user for the parser's vocabulary.

**Priorities.** P1 common construct parsed wrong (corrupts reports silently) ·
P2 common construct missing · P3 exotic construct that should be
recognize-and-diagnose · P4 display/labeling · ok = verdict correct.

**Tallies.** GNU Make: 93 rows — 43 wrong, 13 missing, 4 degrades-honestly, 33 correct.
GitLab CI + robustness: 41 rows — 19 wrong, 12 missing, 4 degrades-honestly, 6 correct.

**Governing invariants for the fixes** (from the review charter):
1. Unknown constructs degrade the smallest possible unit — a value, then a job/rule,
   then a file, in that order. File-level `error` is reserved for input the real
   tool would also reject.
2. References to jobs defined elsewhere become ghosts, never fatalities.
3. If `make -pqn` accepts a file, an "Unparseable line" warning is a parser bug.
4. Parsers terminate on hostile input; cycles are detected and named everywhere
   they can occur.
