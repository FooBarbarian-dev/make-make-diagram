# Trigger docs phase 2: report export buttons + drift check — design

Date: 2026-08-27
Status: implemented (continuation of
`2026-08-27-trigger-docs-design.md`, whose phase-2 list this implements;
as-built notes at the end)

## Scope

The two highest-priority phase-2 items from the trigger-docs spec, plus
the schema addition the first one needs:

1. **"Export scenario"** button in the What-If tab — the tab becomes the
   scenario *authoring* UI: configure knobs interactively, export the
   YAML stanza, paste into the shared scenarios file.
2. **"Copy markdown"** button — the current evaluation (or pinned delta)
   as GitLab-flavored markdown tables, for pasting into issues, MRs and
   wikis.
3. **`pipeview scenarios verify`** — the read-only drift check: compare a
   repo's committed docs against fresh generation, exit non-zero on
   drift, so a scheduled CI job can police freshness.

Still out of scope: per-scenario `projects:` filters, chain-following,
`<details>` traces, `--index-name`.

## Decisions

### Export scenario

- A new DOM-free helper in `whatif.js` — `scenarioYaml(config)` — turns
  the tab's config object into a **complete scenarios file** (header
  comment, `version: 1`, one stanza), so pasting into an empty file works
  and the `- id:` block lifts cleanly into an existing file.
- Only meaningful knobs are emitted (the tab's config always carries
  every key with defaults; the YAML mirrors `to_whatif_config` in
  reverse): event-specific keys, `variables` from overrides, booleans
  only when true, `changed_files` omitted when unspecified.
- The scenario id is derived from the event + ref (`push-main`,
  `tag-v1-2-3`, `mr-feature-x`, `schedule`) with a "rename to taste"
  comment; ids stay `[a-z0-9-]+`.
- **Schema addition:** `changed_files: all` (the literal string) becomes
  valid, meaning "assume every `changes:` pattern matches" — the tab has
  that tri-state knob and the export must be lossless. The docs renderer
  already words the assumption honestly.
- **Round-trip is the contract, semantically:** a node-generated export
  is loaded by the Python loader, mapped through `to_whatif_config`, and
  both configs must produce **identical `evaluate_event` output** on a
  fixture. Key-by-key equality would drown in the tab's defaulted knobs;
  evaluation equality is what lossless actually means.

### Copy markdown

- DOM-free helpers `markdownSummary(report, result, config)` and
  `markdownDiff(report, diff, labelA, labelB)` in `whatif.js`, beside
  `textSummary`/`textDiff` and sharing their vocabulary: **the markdown
  button follows the listing's wording** (`outcomeText`), not the
  trigger-docs renderer's. The committed docs and the pasted snippet are
  different surfaces; each has one source of truth, both inside the
  evaluator that computed the verdicts.
- Shape: a bold what-if header line, one `###` section per candidate
  pipeline (children nested with a "Child pipeline:" prefix), a
  `| Job | Stage | Verdict |` table of the jobs that might run, footers
  for duplicates and not-created pipelines. The delta variant is one
  table with a leading `Δ` column (`+`/`−`/`~`/`=`) and the same
  pipeline-pairing notes `textDiff` prints. No mermaid: the interactive
  graph is a click away in the report, and issues want tables.
- Cell hygiene matches the Python renderer: pipes escaped, job names in
  code spans, one line per cell.
- UI: two toolbar buttons next to **Copy job list**, using the same
  clipboard mechanics (async API, hidden-textarea fallback); if both
  fail, the payload lands selected in the existing text block so a
  manual Ctrl+C always works. The markdown button's label flips to
  **Copy markdown delta** while a baseline is pinned.

### scenarios verify

- `pipeview scenarios verify FILE REPO DOCSDIR` — regenerate docs for
  the checkout at REPO from the scenarios FILE (exactly the generation
  path sync uses), then compare with the committed docs in DOCSDIR.
- Comparison masks the two provenance lines (HTML marker comment and the
  visible "Generated by pipeview" line) on both sides before comparing
  bytes: a doc regenerated by a newer pipeview from the same inputs is
  *not* drift; changed content is.
- Reported per file: **missing** (expected, not present), **stale**
  (content differs), **orphaned** (marker-bearing file no current
  scenario produces). Files without the marker are ignored — they are
  human docs.
- Exit codes: 0 in sync, 1 drift (each drifted file named on stderr),
  2 unusable inputs. Read-only throughout — verify never writes.

## Testing

- `scenarioYaml`: node harness cases (extending the textdiff runner) for
  representative configs, plus the Python round-trip test above
  (node export → loader → `to_whatif_config` → `evaluate_event` equality)
  for every exported config. Skips without node, like the other suites.
- `markdownSummary`/`markdownDiff`: node harness cases pinning table
  shape, escaping (hostile fixture), duplicates/not-created footers, and
  that job ids + verdict words agree with `textSummary` for the same
  evaluation.
- `verify`: pytest over tmp dirs — in-sync (0), stale/missing/orphaned
  (1, each named), non-marker files ignored, provenance-only differences
  ignored, bad inputs (2).

## As-built notes

- **A second schema addition surfaced**: `open_mr` on
  schedule/web/api/trigger scenarios. The tab lets those events carry an
  open MR (CI_OPEN_MERGE_REQUESTS is set in every branch pipeline whose
  branch has one — the documented dedup pattern reads it), so a lossless
  export needs the key there too.
- **`strip_provenance` masks a third thing**: the index's regeneration
  command. It embeds the invocation (sync's flags vs verify's), which
  differs without the content differing — same reasoning as the
  provenance lines.
- **`verify`'s one honest limitation is in its --help**: it parses the
  local checkout, so docs generated by `gitlab sync` for configs that
  lean on cross-repo includes may legitimately differ.
- The markdown table checker in the tests parses body rows with an
  escaped-pipe-aware splitter and pins verdict wording against
  `textSummary` line-by-line — the "same vocabulary" promise is a test,
  not a comment.
